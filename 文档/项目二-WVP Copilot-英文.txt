Project 2: WVP Copilot -- LLM-Based Drone AI Agent System (2025/11 -- 2026/03)
Tech Stack: Python, LangChain, LangGraph, SSE, MCP, FastAPI, DeepSeek API, Redis
Overview: Built for fire emergency command scenarios, this drone AI Copilot deeply integrates software, hardware, and AI algorithms to dramatically lower the barrier to drone operation. Users simply describe their needs in natural language (e.g., "Fly to Lujiazui, zoom 7x, take a photo, then return"), and Copilot accurately understands the intent, autonomously breaks it down into a sequence of drone commands, and orchestrates their execution -- enabling remote control and task dispatch through conversation. Adopts a two-tier architecture: Python (Agent orchestration layer) + Java (device control layer), decoupled via REST communication.

Implementation:

● Async State Synchronization & Deterministic Fault Recovery
  (S) Situation: LLM inference is synchronous (seconds-level), while drone flight is asynchronous (minutes-level). Tool functions that invoke flight commands must wait for actual execution to complete, but wait times vary with flight distance and communication latency.
  (T) Task: Establish reliable state synchronization between LLM synchronous inference and drone async execution, and deterministically judge flight success after timeout to prevent misjudgment that would derail subsequent commands.
  (A) Action: Encapsulated Redis polling waits inside tool functions, dynamically estimating timeout thresholds based on flight distance. Upon timeout, instead of immediately declaring failure, queries the drone's actual OSD position for deterministic fallback: distance to target < 5m judged as arrived (state lag due to communication delay); no position change judged as hardware failure; position still changing extends the wait. Intermediate states are pushed only to the frontend; the LLM is not exposed to them.
  (R) Result: Eliminated uncertainty in async waiting. Deterministic judgment via OSD position after timeout ensures the LLM always makes next-step decisions based on accurate state.

● Cascading Failure Circuit-Breaking & Safety Isolation for Multi-Step Task Chains
  (S) Situation: User commands may be broken into multi-step task chains (fly to location, take photo, return). If any step in the chain fails without circuit-breaking, subsequent steps may execute under abnormal conditions, posing safety risks. Safety-critical operations such as emergency stop must be fully isolated from the LLM to ensure absolute reliability.
  (T) Task: Implement failure circuit-breaking for multi-step task chains -- any step failure immediately stops subsequent execution. High-risk operations require human confirmation. The emergency stop channel must bypass both the Agent and the LLM entirely.
  (A) Action: In the Plan-Confirm-Execute three-phase workflow, any step returning failure or triggering emergency stop immediately breaks and blocks subsequent execution. High-risk operations (flight, return-to-home) enforce Human-in-the-Loop confirmation before execution. The emergency stop command goes through an independent MQTT hardware channel, bypassing the Agent and LLM entirely; the frontend simultaneously closes the SSE connection to achieve session-level isolation.
  (R) Result: Multi-step task chains now have cascading failure circuit-breaking capability. High-risk operations have human fallback. Emergency stop is physically isolated from the LLM, ensuring absolute reliability.

● State Machine-Driven Sub-Task Orchestration Replacing LLM Temporal Decision-Making
  (S) Situation: Orbit flight is inherently a state machine (enter orbit, capture photos at each angle, complete 360 degrees, exit), but LLM inference latency (1-3s per step) at a drone speed of 3m/s would cause photo capture points to drift by 3-9 meters. The ReAct loop relies on LLM for temporal judgment, which is physically infeasible for real-time control scenarios.
  (T) Task: Transfer temporal decision-making authority for real-time control tasks such as orbit flight from the LLM to a deterministic state machine, while preserving the LLM's intent understanding capability.
  (A) Action: Introduced LangGraph to model an explicit conditional subgraph -- enter_orbit, orbit_loop (conditional edge: >=360 degrees exits), exit_orbit. Execution cycles are determined by graph edges; the LLM is responsible only for intent routing, not temporal judgment. The main path (linear tasks) retains AgentExecutor to avoid over-engineering.
  (R) Result: Eliminated photo capture point drift caused by LLM inference latency. Orbit timing precision is guaranteed by graph state transitions. The LLM's role is narrowed to intent understanding.

● MCP External Toolchain & Composite Command Encapsulation
  (S) Situation: Drone control involves multiple external systems (Amap geocoding, device control APIs). A single user intent (e.g., "Record video for 30 seconds") often maps to multiple low-level command sequences (start, countdown, stop). Having the LLM directly orchestrate low-level commands is error-prone and inefficient.
  (T) Task: Integrate external toolchains and encapsulate composite commands to reduce LLM orchestration complexity, enabling the LLM to program against business semantics rather than hardware primitives.
  (A) Action: Integrated Amap Server via the MCP protocol, with 15 map tools auto-registered. Geocoding returns multiple candidates; the LLM arbitrates the best match based on context. Defined 16 drone tool functions using LangChain @tool, following the principle of "exposing business semantics, not hardware primitives" to encapsulate composite commands (e.g., record_for_duration internally orchestrates the complete start, countdown, stop sequence). SSE streaming enables real-time observability of the tool call chain.
  (R) Result: The LLM invokes tools at the business-semantic level. Composite commands simplify common operations from multi-step to single-step. SSE streaming output keeps the operation process transparent to the user.
