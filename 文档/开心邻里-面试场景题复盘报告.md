# 面试场景题分析报告：MySQL 300万条数据导出 Excel 上传 OSS

> 复盘时间：2026-07-03
> 面试公司：开心邻里（杭州）
> 核心问题：场景题回答缺乏结构化思维，方案反复横跳，多次被面试官纠正

---

## 一、原题还原

根据对话推断，题目如下：

> MySQL 有一张大表，符合查询条件的数据约 **300 万条**。通过定时任务触发，需要将这些数据处理后写入 **Excel 文件**并上传到 **OSS**。要求数据完整正确，处理时间尽可能短。表数据持续有新增。

---

## 二、回答过程复盘：逐阶段问题分析

### 阶段 1：未分析瓶颈直接甩方案

**原话**："首先想到的就是一定要用多线程"

**问题**：没有先回答"慢在哪里"。300 万条数据的处理链路是：

| 环节 | 操作 | 瓶颈类型 |
|------|------|---------|
| 读 | 300 万条 × 1KB → 3GB 从 MySQL 读出 | **I/O 瓶颈** |
| 处理 | 数据清洗、格式转换 | 取决于复杂度 |
| 写 | 写入 Excel 文件（含压缩编码） | **CPU + I/O** |
| 传 | 上传 OSS | **网络 I/O** |

整个过程是典型的 **I/O 密集型**场景。磁盘吞吐量和网络带宽是固定的，多线程对 I/O 密集型任务的帮助有限。如果是 CPU 密集型（如每条数据需要复杂计算），多线程才真正有效。

**正确做法**：先分析瓶颈 → 再针对瓶颈选方案。

---

### 阶段 2：提出 MQ，被反问后立刻放弃

**原话**："用 RocketMQ 解耦，避免阻塞主服务"

**面试官反问**："定时任务触发了直接消费不就行了，为什么还要走 MQ？"

**回答**："对对对您说得对，确实没必要"

**问题**：不该立刻投降。MQ 在这个场景下并非完全没道理：

- **需要 MQ 的场景**：数据量大到需要专门的服务实例处理、需要失败重试机制、需要削峰填谷
- **不需要 MQ 的场景**：单个定时任务直接处理，没有并发消费的需求

应该回答：*"在这个 300 万数据量下直接处理就够。但如果数据量再大一个数量级，或者多个定时任务需要统一调度，MQ 做异步解耦就有价值了。"*

**核心问题**：你在被反驳时的模式是"立刻认错"，而非"说明适用条件"。面试官要的不是你永远对，而是你能说清楚"什么情况下选 A、什么情况下选 B"。

---

### 阶段 3：多线程同时写同一个文件（基本常识错误）

**原话**："10 个线程同时往一个 Excel 文件的不同行写入"

**面试官暗示**："多线程能同时写一个文件吗？"

**回答**："应该好像好像不太行…一个文件在被一个线程修改的时候其他会被阻塞"

**问题**：这是一个硬伤。同一个文件句柄不能并发写，加锁后退化回串行，多线程白开。

**正确做法**：如果要多线程并行，每个线程必须操作**独立的文件**，最后一起上传。

---

### 阶段 4：300 万条全读进内存（另一个基本常识错误）

**原话**："把 300 万条数据从数据库读到内存，分成 10 个 List"

**面试官暗示**："300 万条放内存没问题吗？"

**回答**："对对对…确实会有很大压力"

**问题**：300 万行 × 假设每行 500 字节 = **1.5GB**。Java 堆内存直接打满，GC 频繁甚至 OOM。

**正确做法**：游标分批读取 + 流式写入，内存占用与数据总量脱钩。

---

### 阶段 5：提出 Redis 中转，同样没解决内存问题

**原话**："每次读 30 万放到 Redis 里，再慢慢消费"

**问题**：Redis 也是内存存储。数据从 MySQL 搬到 Redis，内存压力从应用服务器转移到 Redis 服务器——本质上没解决问题，反而加了一层网络 I/O 开销。

---

### 阶段 6：Excel 行数上限完全没提

**关键知识点**：Excel 2007+ 的 `.xlsx` 格式，单 Sheet 最大行数为 **1,048,576 行**。300 万条数据无法放进一个 Sheet，至少需要 3 个 Sheet。

全程没提这个上限，面试官可能会认为你对 Excel 文件格式缺乏基本了解。

---

### 阶段 7："合并 Excel"说不清楚

**原话**："合并就是 1 个 Excel 文件里面有 10 个 Sheet"

**问题**：这等于没合并，只是把 10 个文件的问题变成了 10 个 Sheet 的问题。面试官问的是"你怎么汇总成一个结果文件"——你没给出具体方案。

---

### 阶段 8：没把自己的知识串起来

前面 deep pagination 那题你回答得不错（覆盖索引 + 子查询），ES 那段也说得清楚。但场景题里你应该说：

> "MySQL 读取用 keyset pagination，这个其实跟刚刚说的 deep pagination 是一个道理——offset 越大扫描行数越多，keyset 走主键索引每次 O(1) 定位。"

**连接知识点是面试加分项。你没做这个连接。**

---

## 三、核心问题总结

### 技术层面

| 问题 | 严重程度 |
|------|---------|
| 多线程写同一文件（不可能） | 🔴 硬伤 |
| 300 万条全读内存（1.5 GB） | 🔴 硬伤 |
| Redis 中转同样内存爆炸 | 🔴 硬伤 |
| 未提 Excel 单 Sheet 104 万行上限 | 🟡 缺失 |
| 未分析瓶颈（I/O密集 vs CPU密集） | 🟡 缺失 |
| 未连接 deep pagination 经验 | 🟡 缺失 |

### 表达层面

| 问题 | 表现 |
|------|------|

## 四、正确解法

### Step 1：先对齐需求

> "300 万条数据。我确认几个细节：每条数据大概多少字段？处理是指纯查出来写 Excel 还是有业务转换逻辑？定时任务多久触发一次——每天还是每小时？"

### Step 2：分析瓶颈

> "这个场景的核心瓶颈在 MySQL 读取和 Excel 写入，都是 I/O 密集。CPU 侧开销主要在 Excel 压缩编码，不算大。所以优先考虑流式处理而非多线程——多线程对 I/O 密集的帮助有限。"

### Step 3：读取策略（keyset pagination）

```java
Long lastId = 0L;
int batchSize = 10000;

while (true) {
    List<Record> batch = jdbc.query(
        "SELECT * FROM table WHERE id > ? ORDER BY id LIMIT ?",
        lastId, batchSize
    );
    if (batch.isEmpty()) break;

    writeToExcel(batch);  // 流式写入
    lastId = batch.get(batch.size() - 1).getId();
}
```

**为什么不用 offset 分页**：`LIMIT 2000000, 10000` 需要 MySQL 扫描 201 万行后再取 1 万行。keyset 走主键索引，每次 O(1)，300 万行从头到尾读取时间恒定。**这和之前 deep pagination 的解决思路是一致的。**

### Step 4：写入策略（EasyExcel 流式写入）

```java
// EasyExcel 逐行刷盘，内存占用恒定（与数据总量无关）
// 每 100 万行自动切新 Sheet（单 Sheet 上限 ~104 万行）

ExcelWriter writer = EasyExcel.write(outputPath).build();

int rowCount = 0;
int sheetIndex = 0;

while (true) {
    List<Record> batch = readNextBatch();
    if (batch.isEmpty()) break;

    writer.write(batch, EasyExcel.writerSheet(sheetIndex, 
        "数据" + (sheetIndex * 100 + 1) + "万-").build());

    rowCount += batch.size();
    if (rowCount >= 1_000_000) {
        rowCount = 0;
        sheetIndex++;
    }
}
writer.finish();
```

**关键点**：
- 流式写入 = 逐行刷盘，内存占用恒定（不管 300 万还是 3000 万行）
- 每 100 万行自动切新 Sheet（Excel 单 Sheet 上限 ~104 万行）
- 全程不需要把 300 万条放进内存

### Step 5：是否并行

| 场景 | 方案 |
|------|------|
| < 10 万条，单次定时任务 | 单线程流式处理足够 |
| 100 万 ~ 500 万条 | 按 id 范围分片并行：id 1-100万/100万-200万/200万-300万，每个线程独立的游标读 + 独立的文件写，零锁竞争 |
| 持续有新增 | 第一次全量处理后，记录 `last_id`，后续只处理增量（`WHERE id > last_id`）|

**如果并行**：每个线程操作独立的 id 区间 + 独立的输出文件，不存在任何竞争。

### Step 6：上传 OSS（分片上传）

3GB 的 Excel 文件用 OSS 分片上传（multipart upload），避免单次 HTTP 请求超时。

### Step 7：主动说边界条件

> "这个方案的前提是主键 id 单调递增。如果主键是 UUID，keyset 行不通，需要换方案——比如用创建时间字段 + 索引做游标，或者引入 CDC 捕获增量变更。"

## 五、标准回答模板

如果重新回答这道题：

> **① 先对齐**："300 万条数据，我确认一下字段数、处理逻辑、定时频率。"
>
> **② 分析瓶颈**："核心瓶颈在 MySQL 读取和 Excel 写入，都是 I/O 密集。优先流式处理而非多线程。"
>
> **③ 读取**："MySQL 用 keyset pagination，每次 `WHERE id > lastId ORDER BY id LIMIT 10000`。这和 deep pagination 的道理一样——offset 越大越慢，keyset 走主键索引每次 O(1)。"
>
> **④ 写入**："EasyExcel 流式写入，逐行刷盘不占内存。每 100 万行自动切新 Sheet，因为 Excel 单 Sheet 上限 104 万行。"
>
> **⑤ 并行**："如果需要加速，按 id 范围分片并行，每个线程独立读、独立写、零锁。不需要 MQ——单机单任务直接处理就够。"
>
> **⑥ 增量**："第一次全量后记录 last_id 存 Redis，后续定时任务只处理增量。"
>
> **⑦ 边界**："前提是 id 单调递增，UUID 主键需要改用时间字段索引做游标。"

## 六、面试表达的三个改进点

### 1. 拒绝"甩方案 → 被纠正 → 放弃"的模式

下次面试官反问你的方案时，**不要立刻投降**。改成：

> "这个数据量下您的说法是对的，确实不需要 MQ。但如果数据量再大一个数量级、或者需要失败重试，MQ 做异步解耦就有价值了。我提 MQ 是想说明我知道这个选项，不是非用它不可。"

### 2. 结构化输出："框架先行"而非"碎片堆砌"

每次回答场景题按这个结构来：

```
① 对齐需求（确认关键细节）
② 分析瓶颈（慢在哪里）
③ 读的策略（为什么这么读）
④ 写的策略（为什么这么写）
⑤ 是否需要并行（为什么）
⑥ 增量/边界（什么情况下这个方案会失效）
```

面试官要的不是你一口气说出所有方案，而是你这个思考框架。

### 3. 主动连接前面的知识点

> "这个 MySQL 分批读取的问题，其实和我们前面聊的 deep pagination 是同一个根因——offset 分页越往后越慢。keyset pagination 两个场景都能解决。"

这种连接会让面试官觉得你的知识是体系化的，不是背的。
